## История, теги и релизы

> **Связь с прошлым уроком:** ваш проект чист и ухожен. Теперь сделаем его «официальным»: научимся читать историю проекта, правильно нумеровать версии и публиковать релизы на GitHub — ровно как это устроено у настоящего программного обеспечения.

## Цель урока

Освоить работу с историей репозитория: ориентироваться в коммитах, сравнивать версии, понимать семантическое версионирование и публиковать стабильные версии проекта через теги и релизы GitHub.

## Чему вы научитесь к концу урока

- Читать историю через `git log` и рассматривать коммиты через `git show`.
- Сравнивать коммиты и версии через `git diff`.
- Правильно нумеровать версии — семантическое версионирование `MAJOR.MINOR.PATCH`.
- Создавать теги `git tag` и публиковать их на GitHub.
- Создавать Release на GitHub с описанием изменений.

## Блок 1. Чтение истории

Лог коммитов — дневник проекта. Самые важные команды чтения:

### `git log`

```bash
git log            # вся история: кто, когда, что
git log --oneline  # по одной строке на коммит — повседневный вид
git log --graph    # ветки в виде дерева
git log --stat     # какие файлы менялись в каждом коммите
git log -p         # полный diff каждого коммита (долго! симметрично)
```

Пригодятся и фильтры:

```bash
git log --oneline --author="Javlon"      # только коммиты этого автора
git log --oneline --since="2 weeks ago"  # только недавние
git log --oneline -n 5                   # только последние пять
git log --oneline -- README.md           # только коммиты, трогающие README.md
```

**Про-совет:** после `--oneline` добавьте `-g` и увидите *reflog* — лог всего, что происходило в репозитории, включая reset и rebase.

### `git show`

Детальный просмотр одного коммита:

```bash
git show HEAD          # самый свежий коммит
git show 8f3d2c1       # конкретный коммит по хешу
git show HEAD~1        # коммит перед HEAD
```

`HEAD~N` — на N коммитов назад (цепочка родителей). `HEAD~1` равен `HEAD^`.

### `git blame`

Кто написал какую строку:

```bash
git blame README.md
```

Каждая строка показывает коммит, автора и дату последнего касания. Незаменимо, когда нашли баг и нужно понять «кто и зачем поменял эту строку».

## Блок 2. Сравнение версий

`git diff` отвечает на вопрос «что изменилось между двумя точками?».

```bash
git diff                    # рабочая директория vs индекс (что не застейджено)
git diff --staged           # индекс vs последний коммит (что ЗАстейджено)
git diff HEAD               # всё незакоммиченное: staged и не только
git diff 8f3d2c1..4b5a1c2   # между двумя коммитами
git diff v1.0.0 v1.1.0      # между двумя тегами
```

Реальный сценарий: вам пришли правки по Pull Request, и нужно увидеть, что именно приносит ветка ревьюера по сравнению с main:

```bash
git diff main..feature/contact
```

Строки с `-` удалены, с `+` добавлены. Это язык обсуждения кода в командах — на `git diff` говорят все.

## Блок 3. Семантическое версионирование

Как нумеровать версии, чтобы все понимали? Знакомьтесь — **SemVer**, международный стандарт:

```text
MAJOR.MINOR.PATCH        например 1.4.2
```

| Часть | Когда увеличивается |
| --- | --- |
| **MAJOR** | Ломающие изменения — старый код может перестать работать |
| **MINOR** | Новые функции, обратная совместимость сохраняется |
| **PATCH** | Только исправления багов |

Примеры:

- `1.0.0` — первый публичный релиз.
- `1.0.1` — исправили баг, нового ничего нет.
- `1.1.0` — добавили функцию.
- `2.0.0` — что-то сломали; всем, кто использовал `1.x`, нужно провериться.

**Правило:** если у существующих пользователей «может сломаться» — растёт major; если нет — minor или patch.

## Блок 4. Теги

**Тег** — имя, присвоенное конкретному коммиту: закладка в истории, которая не двигается.

### Создание

```bash
git tag v1.0.0              # lightweight-тег
git tag -a v1.0.1 -m "Release 1.0.1"   # annotated-тег
```

| Тип | Содержит | Когда |
| --- | --- | --- |
| **Lightweight** | просто указатель-имя | быстрая метка, черновики |
| **Annotated** | имя + автор + дата + сообщение | настоящие релизы — рекомендовано |

### Просмотр и навигация

```bash
git tag          # список тегов
git tag -l "v1.*" # фильтр
git show v1.0.0  # посмотреть затегированный коммит
git diff v1.0.0 v1.1.0   # что изменилось между релизами
```

### Публикация на GitHub

Теги сами на удалённый не уходят:

```bash
git push origin v1.0.0        # один тег
git push origin --tags        # все теги
```

Удаление тега (локально и на удалённом):

```bash
git tag -d v1.0.0
git push origin --delete v1.0.0
```

**Важно:** тег никогда не должен двигаться — нужна «новая» версия — создавайте новый тег. Переписывание тегов путает всех, кто их уже скачал.

## Блок 5. Релизы и CHANGELOG

Тег — технический, **Release** — для людей. На GitHub: откройте репозиторий → **Releases** → **Draft a new release** → выберите существующий тег (или создайте новый) → напишите описание → опубликуйте.

В описании релиза обычно:

- что нового (фичи);
- что изменилось (улучшения);
- что починено (фиксы);
- ломающие изменения (если вырос major);
- благодарности контрибьюторам.

GitHub автоматически собирает архив (`zip`/`tar.gz`) с затегированным кодом — дистрибутив без папки `.git`.

### CHANGELOG

Многие зрелые проекты ведут `CHANGELOG.md` — хронологический список релизов. Конвенция «Keep a Changelog» рекомендует:

```text
## [Unreleased]
- Планируемые ближайшие изменения

## [1.1.0] - 2026-05-12
### Added
- новая функция
### Fixed
- описание бага
```

CHANGELOG + теги + релизы = проект, который любой поймёт и сможет использовать, не читая исходников.

## Блок 6. Мини-задание

На маленьком учебном проекте:

1. Просмотрите всю историю деревом: `git log --oneline --graph`.
2. Рассмотрите самый первый коммит через `git show`.
3. Создайте annotated-тег `v1.0.0` для текущего состояния.
4. «Опубликуйте» его на удалённом в скрипте-симуляторе.

**Решение:**

```bash
git log --oneline --graph
git show $(git rev-list --max-parents=0 HEAD)   # самый первый коммит
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
```

## Практика

Превратите «tidy-project» из прошлого урока в версионируемый проект:

1. Создайте 3–4 коммита, имитируя разработку функций (например, добавьте `index.html`, затем фикс стилей).
2. Посмотрите историю: `git log --oneline --graph`.
3. Сравните два коммита: `git diff <хеш-1>..<хеш-2>`.
4. Создайте annotated-теги: `v1.0.0` после «достаточно стабильно», затем `v1.0.1` после фикса бага.
5. Имитируйте публикацию: `git push origin --tags` (в скрипте практики remote локальный).
6. Напишите `CHANGELOG.md` с записями для обеих версий.
