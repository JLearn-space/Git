## .gitignore and Project Hygiene

> **Connection with the previous lesson:** you now work in a team and on GitHub. Today we talk about cleanliness — how to keep a repository tidy: which files should never get into it, how to create a clean project structure, and why a `.gitignore` is more important than it seems.

## Block 1. What `.gitignore` Is and Why

**In simple terms:** before a trip you pack a suitcase. You don't put in the trash from the floor, or a third identical jacket "just in case" — you'd have to carry all that with you. `.gitignore` is the "do not pack this" list for the repository.

**.gitignore is a special file** (in the repository root) containing rules for files and folders that Git should **ignore** — not track, not show in `git status`, not accidentally commit.

### Why this matters

- **Machine-generated garbage.** `node_modules` (tens of thousands of files), build output, caches — they're re-created by one command. In the repository they only bloat it.
- **Personal data.** `config.json` with your paths, `.env` with tokens, local databases.
- **OS junk.** `.DS_Store`, `Thumbs.db`, editor files — useful only on your machine.

Real examples:

```text
# Our own Git course files — a real .gitignore
.DS_Store
.obsidian/
.idea/
.vscode/
*.swp
```

Compare the course directory listing with `git status`: the hidden files don't show up because the `.gitignore` already keeps them out — the file works even without you noticing.

---

### Common Beginner Mistakes

| Error | How to Fix |
| --- | --- |
| Ignoring `.gitignore` "until it's a problem" | It's easier to write rules on day one than to clean a bloated repository later |
| Ignoring only to forget a file that got committed earlier | `.gitignore` protects *new* files; already tracked files stay tracked — need `git rm --cached` |
| Putting the entire `.env` example in `.gitignore` but then committing a real one | Never add secrets to the repository at all; ignore them first |
| Deleting `node_modules` globally hoping Git gets lighter | The files come back for any developer running `install` — delete from the repo, not from the disk |

## Block 2. Pattern Syntax

`.gitignore` is a text file where each line is a rule. Let's master the five main patterns that cover 90% of real needs:

### 1. Comment — line starting with `#`

```gitignore
# Node.js dependencies
node_modules/
```

### 2. Exact file name or path

```gitignore
secret.txt            # ignore secret.txt in any folder
docs/private/plan.md  # specific file inside a specific folder
```

### 3. Folder — trailing slash `/`

```gitignore
node_modules/    # ignore the whole folder and everything inside
build/
```

A folder name with a slash ignores it *and everything in it*.

### 4. Asterisk `*` — any characters

```gitignore
*.log        # all .log files
config.*     # config.json, config.yaml, config.yml
```

### 5. Double asterisk `**` — any nesting depth

```gitignore
**/__pycache__/   # __pycache__ in any subfolder
**/tmp            # any file/folder named tmp at any depth
```

### Negation — `!`

A `!` rule can re-enable something ignored by a broader rule:

```gitignore
*.log
!important.log     # ignore all .log, but not important.log
```

Rules are applied **in order**, from top to bottom — a `!` must come after the rule it overrides.

## Block 3. Ready-Made Templates

Instead of writing rules from scratch, real developers take **templates** — GitHub has them for every language. But you still should recognize the main ones:

| Case | Pattern |
| --- | --- |
| macOS junk | `.DS_Store` |
| Node.js dependencies | `node_modules/` |
| Python bytecode/cache | `__pycache__/`, `*.py[cod]` |
| Python virtual environment | `venv/`, `.venv/` |
| Environment variables with secrets | `.env`, `.env.*` |
| Logs | `*.log` |
| Editor/IDE folders | `.idea/`, `.vscode/`, `*.swp` |
| Build output | `dist/`, `build/`, `out/`, `target/` |

**A ready-made template** lives at [github.com/github/gitignore](https://github.com/github/gitignore) — for example, search for `Node.gitignore` or `Python.gitignore`. Copy what you need into your own `.gitignore`.

### Important nuance

Projects that use Git automatically pull the corresponding template when creating a repository on GitHub: in the "New repository" form there's the **Add .gitignore** dropdown. Check it when creating a new repo — it's still worth auditing the result.

## Block 4. Empty Folders and `.gitkeep`

**Git tracks content, not folders.** An empty folder has no commits — create a folder with no files inside, run `git status`, and it won't appear. A remote repository "won't know" about it.

If you need to keep an empty folder (for example, `images/` for a future project), put a placeholder file in it:

```text
images/.gitkeep
```

`.gitkeep` is an empty placeholder file — a widely accepted convention (the name itself says "keep this folder"). The folder now has content and will be tracked.

**Alternative:** instead of `.gitkeep`, some people put a real file there right away — for example, `images/README.md` with a description. This is even more useful.

## Block 5. Project Root Hygiene

A clean repository starts with the root folder. Standard minimal set:

| File/Folder | Purpose |
| --- | --- |
| `README.md` | What the project is, how to run it, links |
| `LICENSE` | Under what terms the code can be used |
| `.gitignore` | What stays out of the repository |
| `src/` or `css/`, `js/`... | Sources organized by type (as in the HTML course) |
| `docs/` | Documentation, if there is a lot of it |

### What a README contains

- **Project name** and one sentence — what it does.
- **Installation** — how to get it running.
- **Usage** — a brief example.
- **License** and author (credit to the course author, by CC BY-NC-SA, if you reuse materials).

**Rule of thumb:** a repository without a README looks abandoned; a repository with a good README looks professional.

## Block 6. Secrets: Never Commit

The most dangerous file you can put in a repository is the one containing **tokens, passwords, API keys**. Here's why it's fatal:

- a committed secret **stays in history forever** — even if you delete it, it remains in the commit;
- the repository may be public — the secret becomes public;
- tools scan GitHub and **automatically detect** leaked keys — after that the provider (GitHub itself, AWS, etc.) can revoke or notify.

### How to work with secrets correctly

1. **Never write a real secret into code.** Put it in an environment variable or a local `.env` file.
2. Add `.env` to `.gitignore` **first**, before creating it.
3. Provide an example without real values: `.env.example` with `KEY=` placeholders — commit that safely. For this, add a negation rule to `.gitignore` (we met `!` in block 2):

```gitignore
# .gitignore
.env
.env.*
!.env.example    # the example without secrets is committed safely
```

```text
# .env.example — committed safely
API_KEY=
DATABASE_URL=
```

If a secret *has* already been committed — **rotate it** (issue a new one in the service settings) immediately, and only then remove it. Deleting the history alone is not enough.

## Block 7. Mini-Task

For a learning project "write your own mini-site", create the `.gitignore` yourself:

1. Ignore `.DS_Store` and `.vscode/`.
2. Ignore the `build/` folder.
3. Ignore all `.log` files, but keep `important.log`.
4. Do **not** ignore `src/`.

**Solution:**

```gitignore
.DS_Store
.vscode/
build/
*.log
!important.log
```

## Lesson Summary

Today you learned:

- **`.gitignore`** — the "do not pack" list: what Git won't track.
- Patterns: comments (`#`), folders (`name/`), `*`, `**`, negation (`!`) applied in order.
- Ready templates for Node.js, Python, macOS, and editors.
- Git ignores **empty folders** — `.gitkeep` placeholder keeps them in the repository.
- A clean root: README, LICENSE, `.gitignore`, organized folders.
- **Secrets are never committed** — `.env` is ignored first, and a leaked key is rotated.
