## .gitignore и гигиена проекта

> **Связь с прошлым уроком:** теперь вы работаете в команде и на GitHub. Сегодня поговорим о чистоте — как содержать репозиторий в порядке: какие файлы никогда не должны в него попадать, как создать аккуратную структуру проекта и почему `.gitignore` важнее, чем кажется.

---

## Цель урока

Научиться содержать репозиторий чистым: писать правила `.gitignore`, оформлять корень проекта и — главное — не допускать утечек секретов и машинно-генерируемых файлов.

## Чему вы научитесь к концу урока

- Объяснять, что делает `.gitignore` и почему это не роскошь.
- Писать базовые паттерны `.gitignore`: комментарии, папки, `*`, `**`, отрицание `!`.
- Держать пустые папки под контролем версий с помощью `.gitkeep`.
- Собирать аккуратный корень проекта: README, LICENSE, папки.
- Понимать, почему секреты и токены нельзя коммитить никогда.

## Блок 1. Что такое `.gitignore` и зачем

**Простыми словами:** перед поездкой вы собираете чемодан. Вы не кладёте туда мусор с пола или третью такую же куртку «на всякий случай» — всё это пришлось бы тащить с собой. `.gitignore` — это список «не класть в чемодан» для репозитория.

**`.gitignore` — это особый файл** (в корне репозитория) с правилами для файлов и папок, которые Git должен **игнорировать** — не отслеживать, не показывать в `git status`, не коммитить случайно.

### Зачем это нужно

- **Машинный мусор.** `node_modules` (десятки тысяч файлов), результаты сборки, кэши — они пересоздаются одной командой. В репозитории они только его раздувают.
- **Личные данные.** `config.json` с вашими путями, `.env` с токенами, локальные базы данных.
- **Мусор ОС.** `.DS_Store`, `Thumbs.db`, файлы редакторов — полезны только на вашей машине.

Реальные примеры:

```text
# Наши собственные файлы курса — настоящий .gitignore
.DS_Store
.obsidian/
.idea/
.vscode/
*.swp
```

Сравните список папки курса с `git status`: скрытые файлы не показываются, потому что `.gitignore` уже их держит — файл работает, даже когда вы его не замечаете.

---

### Частые ошибки новичков

| Ошибка | Как исправить |
| --- | --- |
| Откладывать `.gitignore` «до проблемы» | Правила проще написать в первый день, чем чистить раздутый репозиторий потом |
| Игнорировать, но забыть, что один файл закоммичен раньше | `.gitignore` защищает *новые* файлы; уже отслеживаемые остаются — нужен `git rm --cached` |
| Положить в `.gitignore` пример `.env`, но закоммитить настоящий | Секреты вообще нельзя добавлять в репозиторий; сначала игнорировать |
| Удалить `node_modules` на диске в надежде, что Git похудеет | Файлы вернутся при первой же `install` — удаляйте из репозитория, а не с диска |

## Блок 2. Синтаксис паттернов

`.gitignore` — текстовый файл, где каждая строка — правило. Освоим пять главных паттернов, покрывающих 90% реальных потребностей:

### 1. Комментарий — строка с `#`

```gitignore
# Зависимости Node.js
node_modules/
```

### 2. Точное имя файла или путь

```gitignore
secret.txt            # игнорировать secret.txt в любой папке
docs/private/plan.md  # конкретный файл в конкретной папке
```

### 3. Папка — слэш `/` в конце

```gitignore
node_modules/    # игнорировать всю папку целиком
build/
```

Имя папки со слэшем игнорирует её *и всё внутри*.

### 4. Звёздочка `*` — любые символы

```gitignore
*.log        # все файлы .log
config.*     # config.json, config.yaml, config.yml
```

### 5. Двойная звёздочка `**` — любая глубина вложенности

```gitignore
**/__pycache__/   # __pycache__ в любой подпапке
**/tmp            # любой файл или папка tmp на любой глубине
```

### Отрицание — `!`

Правило `!` может вернуть то, что отменило более широкое правило:

```gitignore
*.log
!important.log     # игнорировать все .log, кроме important.log
```

Правила применяются **по порядку**, сверху вниз — `!` должно стоять после правила, которое оно переопределяет.

## Блок 3. Готовые шаблоны

Вместо написания правил с нуля реальные разработчики берут **шаблоны** — для каждого языка на GitHub есть свой. Но основные всё же стоит узнавать:

| Случай | Паттерн |
| --- | --- |
| Мусор macOS | `.DS_Store` |
| Зависимости Node.js | `node_modules/` |
| Байткод/кэш Python | `__pycache__/`, `*.py[cod]` |
| Виртуальное окружение Python | `venv/`, `.venv/` |
| Переменные окружения с секретами | `.env`, `.env.*` |
| Логи | `*.log` |
| Папки редакторов/IDE | `.idea/`, `.vscode/`, `*.swp` |
| Результаты сборки | `dist/`, `build/`, `out/`, `target/` |

**Готовый шаблон** живёт на [github.com/github/gitignore](https://github.com/github/gitignore) — например, поищите `Node.gitignore` или `Python.gitignore`. Скопируйте нужное в свой `.gitignore`.

### Важный нюанс

Проекты на GitHub подхватывают соответствующий шаблон автоматически при создании репозитория: в форме «New repository» есть выпадающий список **Add .gitignore**. Воспользуйтесь им при создании нового репозитория — результат всё равно стоит проверить.

## Блок 4. Пустые папки и `.gitkeep`

**Git отслеживает содержимое, а не папки.** В пустой папке нет коммитов — создайте папку без файлов внутри, выполните `git status`, и она не появится. Удалённый репозиторий «не узнает» о ней.

Если нужно сохранить пустую папку (например, `images/` для будущего проекта), положите в неё файл-заглушку:

```text
images/.gitkeep
```

`.gitkeep` — пустой файл-заглушка, общепринятая конвенция (само название говорит: «сохрани эту папку»). Теперь в папке есть содержимое — она будет отслеживаться.

**Альтернатива:** вместо `.gitkeep` некоторые сразу кладут в пустую папку реальный файл — например, `images/README.md` с описанием. Это ещё полезнее.

## Блок 5. Гигиена корня проекта

Чистый репозиторий начинается с корневой папки. Стандартный минимальный набор:

| Файл/Папка | Назначение |
| --- | --- |
| `README.md` | Что это за проект, как запускать, ссылки |
| `LICENSE` | На каких условиях можно использовать код |
| `.gitignore` | Что не попадает в репозиторий |
| `src/` или `css/`, `js/`... | Исходники, разложенные по типам (как в курсе HTML) |
| `docs/` | Документация, если её много |

### Что содержит README

- **Название проекта** и одно предложение о том, что он делает.
- **Установка** — как его запустить.
- **Использование** — краткий пример.
- **Лицензия** и автор (по CC BY-NC-SA — упоминание автора курса, если используете материалы).

**Правило:** репозиторий без README выглядит заброшенным; с хорошим README — профессиональным.

## Блок 6. Секреты: никогда не коммитить

Самый опасный файл, который можно положить в репозиторий, — тот, где лежат **токены, пароли, ключи API**. Почему это фатально:

- закоммиченный секрет **навсегда остаётся в истории** — даже если его удалить, он останется в коммите;
- репозиторий может быть публичным — секрет становится публичным;
- инструменты сканируют GitHub и **автоматически находят утёкшие ключи** — после этого провайдер (сам GitHub, AWS и т.д.) может их отозвать или уведомить.

### Как правильно работать с секретами

1. **Никогда не пишите настоящий секрет в код.** Кладём его в переменную окружения или локальный файл `.env`.
2. Добавьте `.env` в `.gitignore` **сначала**, ещё до его создания.
3. Приложите пример без реальных значений: `.env.example` с плейсхолдерами `KEY=` — его коммитить безопасно. Для этого добавьте в `.gitignore` правило отрицания (познакомились с `!` в блоке 2):

```gitignore
# .gitignore
.env
.env.*
!.env.example    # пример без секретов коммитится безопасно
```

```text
# .env.example — коммитится безопасно
API_KEY=
DATABASE_URL=
```

Если секрет *уже* закоммичен — немедленно **rotайте** его (выпустите новый в настройках сервиса), и только потом удаляйте. Очистить только историю недостаточно.

## Блок 7. Мини-задание

Для учебного проекта «напишем свой мини-сайт» создайте `.gitignore` самостоятельно:

1. Игнорируйте `.DS_Store` и `.vscode/`.
2. Игнорируйте папку `build/`.
3. Игнорируйте все файлы `.log`, но сохраните `important.log`.
4. **Не** игнорируйте `src/`.

**Решение:**

```gitignore
.DS_Store
.vscode/
build/
*.log
!important.log
```

## Итоги урока

Сегодня вы узнали:

- **`.gitignore`** — список «не класть в чемодан»: что Git не будет отслеживать.
- Паттерны: комментарии (`#`), папки (`имя/`), `*`, `**`, отрицание (`!`) по порядку.
- Готовые шаблоны для Node.js, Python, macOS и редакторов.
- Git игнорирует **пустые папки** — заглушка `.gitkeep` сохраняет их в репозитории.
- Чистый корень: README, LICENSE, `.gitignore`, аккуратные папки.
- **Секреты не коммитят никогда** — сначала игнорируют `.env`, а утёкший ключ rotают.

## Практика

Создайте учебный репозиторий «tidy-project»:

1. `git init` и напишите `.gitignore` с паттернами из мини-задания.
2. Создайте пустые папки `src/`, `images/` с `.gitkeep` и файлы `README.md`, `.env.example`, `important.log`, `debug.log`.
3. Выполните `git status` и проверьте, какие файлы Git видит, а какие игнорирует.
4. Закоммитьте подходящие файлы. Убедитесь, что `debug.log` и `.env` в коммите нет.
5. Попробуйте отрицание: добавьте `!important.log`, если его ещё нет в `.gitignore`, и перепроверьте `git status`.
